# Crowd, pose and interaction pipeline audit

Audit date: 21 October 2026. Scope: read-only repository/configuration/licence and local engineering research under [PROTOCOL.md](PROTOCOL.md). No inference, training, GPU access, package installation, weight download, external messaging or service changes were performed. Only this report was written. Recommendations below are proposals, not implemented changes or measured performance.

**Recommendation:** use the existing 17-joint RTMO body7 ONNX path as the first crowd-observation engineering baseline. Stage tracked, bounded interaction crops/windows for a separate ST-GCN research adapter, with PoseC3D as a more expensive comparison. CrowdPose-specific RTMO is a pose-quality experiment requiring a 14-joint adapter and export work, not a ready fight detector. Do not adopt meet-soni5720/Fight-Detection as a replacement. None of these sources establishes physical-fight detection among 50–100 people in compressed near-IR or low-light colour CCTV.

## RTMO and CrowdPose: useful observer, not fight classifier

RTMO is a one-stage person-pose system, avoiding a top-down pose call for every detector box. That makes it a useful engineering foundation for dense scenes, while postprocessing, tracking and action costs still grow with observations. Published V100 pose latency/AP cannot be transferred to GTX 1660 Ti fight detection. See the pinned [RTMO project documentation](https://github.com/open-mmlab/mmpose/blob/759b39c13fea6ba094afc1fa932f51dc1b11cbf9/projects/rtmo/README.md).

**Critical joint-layout distinction:** [RTMO-m CrowdPose config](https://github.com/open-mmlab/mmpose/blob/759b39c13fea6ba094afc1fa932f51dc1b11cbf9/configs/body_2d_keypoint/rtmo/crowdpose/rtmo-m_16xb16-700e_crowdpose-640x640.py#L260) and even [body7→CrowdPose RTMO-l](https://github.com/open-mmlab/mmpose/blob/759b39c13fea6ba094afc1fa932f51dc1b11cbf9/configs/body_2d_keypoint/rtmo/crowdpose/rtmo-l_16xb16-700e_body7-crowdpose-640x640.py#L437) output 14 joints. In order: left/right shoulder, left/right elbow, left/right wrist, left/right hip, left/right knee, left/right ankle, top of head, neck. [Dataset definition](https://github.com/open-mmlab/mmpose/blob/759b39c13fea6ba094afc1fa932f51dc1b11cbf9/configs/_base_/datasets/crowdpose.py#L13).

The existing [body7 RTMO-m config](https://github.com/open-mmlab/mmpose/blob/759b39c13fea6ba094afc1fa932f51dc1b11cbf9/configs/body_2d_keypoint/rtmo/body7/rtmo-m_16xb16-600e_body7-640x640.py#L467) outputs COCO-17. Its order is nose, left/right eye, left/right ear, left/right shoulder, left/right elbow, left/right wrist, left/right hip, left/right knee, left/right ankle. NIVRA's drawing and shoulder/wrist indices assume this layout ([pipeline.py:10–12](../../nivra/pipeline.py#L10), [pipeline.py:86–91](../../nivra/pipeline.py#L86)). Directly substituting CrowdPose-14 would produce incorrect indices and potentially out-of-range access. Map the twelve compatible limb joints explicitly, mark unavailable COCO facial points with zero confidence, and do not substitute head-top/neck as nose/face measurements. A 14-joint graph trained for that layout is a different model, not a config-only use of a COCO-17 checkpoint.

**Hidden export cap:** both the [MMDeploy ONNX config](https://github.com/open-mmlab/mmdeploy/blob/3f8604bd72e8e15d06b2e0552fe2fdb8f8de33c4/configs/mmpose/pose-detection_rtmo_onnxruntime_dynamic.py#L16) and [TensorRT config](https://github.com/open-mmlab/mmdeploy/blob/3f8604bd72e8e15d06b2e0552fe2fdb8f8de33c4/configs/mmpose/pose-detection_rtmo_tensorrt-fp16_dynamic-640x640.py#L28) set `keep_top_k=50`, `max_output_boxes_per_class=200`, `pre_top_k=2000`. The [rewrite](https://github.com/open-mmlab/mmdeploy/blob/3f8604bd72e8e15d06b2e0552fe2fdb8f8de33c4/mmdeploy/codebase/mmpose/models/heads/rtmo_head.py#L67) uses model `max_per_img` when provided, otherwise that export limit. A research export must explicitly set and validate ≥100 retained detections and a sufficient pre-NMS budget. The downloaded local ONNX graph was not parsed, so its actual baked output cap is unverified; upstream defaults are not proof of that artifact's graph.

The pinned MMPose README names an ONNX export file ending `dynamic-640x640.py`, but that exact filename is absent at the inspected MMDeploy pin (HTTP 404). The real file is `pose-detection_rtmo_onnxruntime_dynamic.py`. It inherits base ONNX configuration; an isolated export must explicitly verify 640×640 input metadata and output dimensions, not assume the filename makes them correct.

MMAction2's [init path](https://github.com/open-mmlab/mmaction2/blob/a5a167dff2399e2d182a60332325f9c0d4663517/mmaction/apis/inference.py#L44) delegates checkpoint loading to MMEngine; this audit does not certify that path as `weights_only=True`. Do not treat an unknown `.pth` as safe merely because a config is available. Review the selected loader and use only trusted, pinned state dictionaries with safe loading or controlled conversion.

**Class order:** both selected models use the pinned [60-line NTU label map](https://github.com/open-mmlab/mmaction2/blob/a5a167dff2399e2d182a60332325f9c0d4663517/tools/data/skeleton/label_map_ntu60.txt), in file order with zero-based logits. Relevant indices are **49 punching/slapping another person, 50 kicking another person, 51 pushing another person**. Nearby confounders include 52 pat on back, 53 pointing at another person, 54 hugging, 55 giving something, 56 touching another person's pocket, 57 handshaking, 58 approaching and 59 separating. Preserve all 60 outputs; any fight aggregation, threshold or temporal policy must be fixed before evaluation. These softmax scores are not calibrated probabilities of a physical fight; a forced closed-set top class cannot establish normality or contact.

**Crowd limitations in actual code:** [FormatGCNInput:425–436](https://github.com/open-mmlab/mmaction2/blob/a5a167dff2399e2d182a60332325f9c0d4663517/mmaction/datasets/transforms/formatting.py#L425) truncates to two; increasing this to 100 alone is not a trained crowd-interaction model. [STGCN forward](https://github.com/open-mmlab/mmaction2/blob/a5a167dff2399e2d182a60332325f9c0d4663517/mmaction/models/backbones/stgcn.py#L223) reshapes people into the batch axis and [GCNHead:60–64](https://github.com/open-mmlab/mmaction2/blob/a5a167dff2399e2d182a60332325f9c0d4663517/mmaction/models/heads/gcn_head.py#L60) averages their features. There are no explicit learned inter-person graph edges in this inspected path. Whole-crowd averaging risks diluting one fighting pair.

PoseC3D avoids that two-person formatter but [heatmap generation](https://github.com/open-mmlab/mmaction2/blob/a5a167dff2399e2d182a60332325f9c0d4663517/mmaction/datasets/transforms/pose_transforms.py#L209) fuses multiple people's same-joint heatmaps. A whole-crowd compacted 64×64 heatmap can collapse small/occluded interactions. Some other dataset configs use `DecompressPose(max_person=10)`; that transform's cap is not present in the selected NTU config and should not be misreported as a universal PoseC3D limit.

**Do not use the stock skeleton demo as the live crowd pipeline.** It runs separate human detection and top-down pose inference over an extracted video, defaults detector confidence to 0.9, resizes video short side to 480, and returns a whole-video action label. [Demo](https://github.com/open-mmlab/mmaction2/blob/a5a167dff2399e2d182a60332325f9c0d4663517/demo/demo_skeleton.py#L29). The [skeleton inference API](https://github.com/open-mmlab/mmaction2/blob/a5a167dff2399e2d182a60332325f9c0d4663517/mmaction/apis/inference.py#L142) places each frame's detections into person slots by enumeration, with no temporal ID association. That may suffice for identity-agnostic heatmaps but does not establish stable trajectories for a GCN. Supply NIVRA's tracked slots explicitly, use pixel coordinates rather than feeding its normalized [0,1] coordinates directly to `PreNormalize2D`, preserve confidence/missing observations, and reset on source-time gaps.

For later parent-controlled reproduction, use these exact config/checkpoint/label-map triplets with the pinned `mmaction.apis.init_recognizer` and `inference_skeleton` contracts. Override stock demo defaults explicitly if the demo is used as a reference. A one-clip/no-flip throughput experiment is reasonable but is a **different inference policy** from the shipped 10-clip/20-view benchmark; label and compare it separately. Uniform frame count is not a duration contract: use actual source timestamps to form equal-duration windows and record duplication when fewer observations exist. Do not stretch a short or gapped observation sequence into claimed continuous motion.

## meet-soni5720/Fight-Detection: reject as an adoption candidate

The [README](https://github.com/meet-soni5720/Fight-Detection/blob/9489e9c31d9082d6556164b558452046a62d2aeb/README.md) describes a ResNet152→LSTM binary classifier and a PoseNet exploration. Its headline test percentage is not ranked against another dataset, and no 50–100-person or real night/IR test is established.

* **Actual runnable CRNN path:** [test.py:54–66](https://github.com/meet-soni5720/Fight-Detection/blob/9489e9c31d9082d6556164b558452046a62d2aeb/fight_detection_using_crnn/test.py#L54) constructs ImageNet ResNet152 without the classifier, 7×7 average pooling/flattening, then loads an HDF5 decoder. [Training](https://github.com/meet-soni5720/Fight-Detection/blob/9489e9c31d9082d6556164b558452046a62d2aeb/fight_detection_using_crnn/rnn_training.py#L42) defines input 40×2048, LSTM 1024 then 512, two 256-unit dense blocks and one sigmoid output. [Feature extraction:118–121](https://github.com/meet-soni5720/Fight-Detection/blob/9489e9c31d9082d6556164b558452046a62d2aeb/fight_detection_using_crnn/feature_extraction.py#L118) labels violence=1, other=0. Demo class order is 0 no fight, 1 fight, with sigmoid threshold **0.3**, not a standard 0.5.
* **Preprocessing mismatch:** training loads JPEGs via PIL into RGB arrays without `/255` before encoder feature extraction ([feature_extraction.py:39–58](https://github.com/meet-soni5720/Fight-Detection/blob/9489e9c31d9082d6556164b558452046a62d2aeb/fight_detection_using_crnn/feature_extraction.py#L39), [102–108](https://github.com/meet-soni5720/Fight-Detection/blob/9489e9c31d9082d6556164b558452046a62d2aeb/fight_detection_using_crnn/feature_extraction.py#L102)). Webcam inference resizes OpenCV BGR to 224×224 nearest-neighbour, divides by 255 and never applies the same RGB conversion or ResNet preprocessing ([test.py:118–137](https://github.com/meet-soni5720/Fight-Detection/blob/9489e9c31d9082d6556164b558452046a62d2aeb/fight_detection_using_crnn/test.py#L118)). Training frame strides vary by clip length, whereas inference consumes consecutive webcam frames. Correct intended preprocessing cannot be inferred from the README; checkpoint parity is unresolved.
* **Released asset is a pointer:** [fd_v2.h5](https://github.com/meet-soni5720/Fight-Detection/blob/9489e9c31d9082d6556164b558452046a62d2aeb/fight_detection_using_crnn/model/fd_v2.h5) is a 134-byte Git LFS pointer declaring **191,278,984 bytes** and SHA-256 `991e0548b61043b13f21223f3ca41cac9397feed125356d18da28eab8e051893`. [Posenet/README](https://github.com/meet-soni5720/Fight-Detection/blob/9489e9c31d9082d6556164b558452046a62d2aeb/Posenet/README.md) credits Google and rwightman's pose code. No separate checkpoint licence, source-video rights, releases or reproducible recording-level test split was established. ## Bounded research changes proposed for 50–100 visible people

These changes require a later authorized implementation, isolated from the live public demo.

1. **Separate budgets and measurement.** Keep detector proposals, active tracks, pose observations, action proposals and rendered tracks distinct. Add a research-only 100-person profile through `Header.maxPeople`, runtime capacity, `Pipeline.process` and classroom caller together, after verifying/exporting the model's post-NMS cap. Preserve bounded frame bytes/pixels, timestamps and backpressure. For native 1080p research, use a separately bounded local/offline ingress; do not silently relabel 1280px input as native 1080p. Validate native 1080p/720p and derived 480p separately with source dimensions and person pixel heights.
2. **Keep global detection; spend resolution on spatially fair views.** Start with one global RTMO pass for broad observation, then a fixed budget of native-resolution overlapping tiles or crops chosen by both demand and time since last service. Record overlap and source coordinate transforms, deduplicate across tiles, and test NMS sensitivity in crowded contact. At 640 input, native 1920 width scales person height by about 1/3; 1280 width by 1/2; a 100px-tall source person becomes roughly 33px or 50px before pose. These are geometric examples, not measured accuracy. No upscale restores lost 480p detail.
3. **Build bounded local interaction proposals, not all pairs.** Use a spatial hash/grid or an indexed radius query over boxes expanded by a scale-aware proximity margin; retain up to `k=4` neighbours per track, deduplicate pair IDs and cluster overlaps. This bounds directed proposals by `N*k` (≤400 for N=100), versus 4,950 undirected exhaustive pairs. A naive grid can still degrade quadratically if one dense cell is fully scanned: bound cell occupancy/query work, allow multiscale cells, and report capped candidate counts. Use the same neighbour index for ambiguity and target selection. Detector NMS and tracker association can still be superlinear; profile them separately rather than claiming end-to-end O(N).
4. **Never claim selected pairs cover the crowd.** Maintain a fixed action-work budget, for example a small batch of two-person GCN proposals or small spatial clusters per scheduling tick, plus periodic global RGB checks. Prioritize visible approach/contact/motion and observation quality, but reserve quota for oldest unserved regions so quiet/far fights are not permanently starved. Selection heuristics can miss low-motion grappling; measure that explicitly. Start with conservative batch size 1 and a parent-measured budget, not a hard-coded promise that 100 people are all classified every 400 ms.
5. **Use track-consistent causal skeleton windows.** Store COCO-17 x/y/confidence per source timestamp for 50–100 tracks with explicit absent/ambiguous samples; do not fabricate limbs or interpolate through substantial gaps. Form a pair window with stable person slots and known coordinate frame. Feed the exact selected action config's pixel/normalization contract. For context-rich clusters, compare bounded RGB crops and PoseC3D heatmaps rather than increasing ST-GCN's person count to 100. Stock ST-GCN lacks inter-person graph edges, so it is a compact baseline, not proof of relational reasoning.
6. **Give every view an age and deadline.** Report detected candidates, returned tracks, analyzed people, pose-confident people, selected interaction proposals, omitted proposals, dropped/replaced frames, per-region last analyzed source time, source-time window gaps, queue/inference times and maximum stale age. Analyzed/current-tracker ratio is not visible-human recall. Use manually annotated visible counts and event regions for that denominator. Preserve `limited/unknown` whenever a region exceeded its budget or deadline. Whole-frame X3D score must remain scene evidence with no invented actor attribution.
7. **Measure alerts and coverage independently.** Freeze thresholds/window policy before comparison; measure missed physical-fight events, false alerts/hour, time-to-alert, localization overlap/recall, visible-human detection/pose coverage by person pixel height/occlusion, proposal recall, scheduling starvation and peak CPU/GPU memory. Crowd normal negatives must include jostling, queues, hugs, assistance, play and gesturing. Source-disjoint actor/session/camera groups are required for a future holdout. Existing four-recording diagnostics and the single unresolved VID cohort remain development material.

* **Likely lowest integration cost:** existing RTMO-m ONNX, batch 1, serialized with a small skeleton classifier. A smaller RTMO-s could be a later measured speed/pose-quality tradeoff, not an automatic improvement.
* **ST-GCN:** checkpoint about 12.5 MB, two-person skeleton inputs and batch-1 inference make a 6 GB experiment plausible. That is an engineering estimate, not a verified fit/throughput result. One 17×48×64×64 FP32 input is **12.75 MiB**; 10 clips with mirrored heatmaps total about **255 MiB of raw input** before activations and framework overhead. Sequential/microbatched evaluation is more plausible than stock multi-view concurrent crowd-region processing. Changing view count must be declared. VRAM fit alongside the resident live X3D/other models is not established.
* **CrowdPose RTMO-l:** larger weights and additional export/mapping work make it a lower priority than validating current RTMO-m coverage. No training-fit estimate is made.
* **Fight-Detection CRNN:** ResNet152 plus large LSTMs, old TensorFlow/Keras and preprocessing/licence gaps offer no compelling advantage over the existing PyTorch stack. Windows GPU compatibility and the actual weight payload are unverified; deprioritize rather than porting first.

## Final shortlist, blockers and exact unverified claims

1. **First engineering experiment:** existing COCO-17 RTMO-m body7 observer + bounded native-resolution spatial scheduling + explicit coverage telemetry. This addresses observable engineering gaps; it makes no fight-accuracy claim.
